# PR：产品售价管控 / 低价特批 / 支付方式与收款码防篡改

## 标题

`feat(ops): 增值业务产品售价管控、低价特批文件与支付方式/收款码防篡改`

## 动机

1. 供应链商品需要统一的售价管控：按 SCM 商品维护销售价、零售底价、集团最低价，并映射 `PRODUCT_CATEGORY` 字典品类。
2. 员工 H5 制单时售价应自动带出标准价；低于标准价必须上传特批文件并填写提成比例，且需服务端二次校验，防止前端绕过。
3. 原有“是否收款”无法表达收款渠道，改为支付方式（二维码/现金/转账）；二维码收款码需要鉴权访问并在每次展示时做 SHA-256 防篡改校验。
4. 特批文件需要留痕（上传人、时间、原文件名），便于审计。

## 模块级变更

### 数据库（`ops-platform-project`）

- 新增 `sql/migrate_product_price_payment_qr.sql`（执行库 `mall_db`）：
  - `ops_product_price`：按 `(corp_id, product_id)` 唯一，保存 SCM 商品冗余品牌/型号、字典品类、三档价格、状态、备注。
  - `ops_business_special_file`：特批文件留痕（原始文件名、URL、大小、MIME、上传人、上传时间）。
  - `ops_payment_qr_config`：按运营商组织保存收款码路径、SHA-256、上传人/时间。
  - `ops_business_order.payment_method`、`ops_business_order_item.payment_method`、`standard_sale_price`、`special_file_id/url/name` 及索引。
  - 生产 MySQL 8.0.46 使用 `information_schema` 条件化 `PREPARE`，可重复执行。

### 后端（`ops-platform-project/backend`）

- 新增 `ProductPriceController`（`/api/ops/admin/product-price`）：列表/筛选、SCM 商品搜索、新增、编辑、启停、逻辑删除。
- 新增 `ProductPriceService`/`Impl`：运营商归属、价格关系校验（销售价 ≥ 零售底价 ≥ 集团最低价，均 > 0）、重复商品拦截、逻辑删除行恢复、员工侧查价。
- 新增 `AdminPaymentQrController`、`EmployeePaymentQrController`：收款码元数据/上传/鉴权取图；员工仅可访问所属运营商收款码。
- 新增 `PaymentQrService`/`Impl`：JPG/PNG ≤5MB，SHA-256 登记；**收款码存私有目录**（不在 `/uploads` 静态映射下），每次读取重算哈希，不一致拒绝并 `log.error` 告警。
- 新增 `BusinessSpecialFileService`/`Impl`：PDF/JPG/PNG ≤10MB，PDF 魔数/图片可解码校验；记录上传人、时间、原文件名；订单提交按 `fileId` 校验组织归属。
- 新增 `PaymentMethod` 枚举（`QR/CASH/TRANSFER`），兼容中文/代码入参，落库统一代码。
- 扩展 `ScmBaseDataClient`：SCM 商品分页搜索、按商品 ID 查询权威资料、`requireMaterialById` 校验 `productId` 与品牌/品类/型号同源；ID 兼容数字/字符串，型号为空时以商品名称兜底。
- 改造 `EmployeeBusinessEntryServiceImpl`：
  - 每行产品查产品售价；未配置/停用直接拒绝制单。
  - 售价低于标准价自动判定特批，强制校验特批文件归属 + 提成比例 0~100（后端二次校验，忽略前端 `isSpecial`）。
  - 订单/明细写入支付方式；零售底价/集团最低价统一取产品售价表，移除手工单对旧 `ops_value_added_product` 底价的兜底，避免双价源。
  - 保留多产品 × 多经办人拆行、订单编号/批次、会员匹配、流程发起等既有能力。
- `BusinessOrderService.createOrder` 增加 `paymentMethod` 参数；手工/Excel 导入/历史补建 3 处调用同步。
- `ScmSaleReturnSyncServiceImpl` 生成退货负数分录时继承标准售价、特批文件与支付方式，保证导出/审计口径一致。
- 订单视图返回 `paymentMethod/paymentMethodName`、产品 `standardSalePrice`、特批文件信息；异步与同步导出表头均增加“支付方式/特批文件”（31 列）。

### 员工 H5（`ops-platform-project/frontend`）

## 影响范围

- 员工手工新增业务：**未配置售价的商品将无法制单**（需求选定的阻止策略）；低价但无特批文件/提成比例同样拒绝。
- 手工单零售底价/集团最低价来源改为 `ops_product_price`，提成分档可能随之变化；上线前需完成核心商品售价配置。
- 导出列数 29 → 31，新增支付方式/特批文件；下游如按列号解析需同步调整。
- 新增 3 个控制器、3 张表、5 个订单/明细列；Excel 导入链路不受影响（支付方式为空，历史 `is_received` 保留）。
- SCM 商品信息 DTO 无图片字段，产品售价列表暂不展示商品图片（需求为“如商品信息有”）。
- 转账流水号/现金备注本期未新增独立字段，可复用订单备注；后续按业务需要扩展。
- `is_received` 仍用于财务核对节点（历史资金到账确认）；员工制单 UI/请求已完全移除。

## 代码审查修复记录

- 特批文件 URL 改为 `/uploads/ops/special-approval/...`：生产 host nginx 仅把 `/uploads/ops/` 反代到 ops，原 `/uploads/special-approval/` 会在生产 404/串到 mall。
- 新代码统一使用 `com.aip.sdk.exception.BusinessException`：`com.aip.common` 的异常 handler 未被 SDK 导入/组件扫描，原写法会被兜底成 500「系统内部错误」，所有售价/特批/收款码提示都会丢失。
- 商品行增加稳定 `uid` 作为 v-for key，避免删除中间行后 Vue 复用组件导致价格状态写错行。
- 标准价查询增加请求 token；草稿/步骤回显按最新标准价重判，但保留用户已填价格与特批附件，避免 7 天草稿使用过期标准价。
- 价格查询无法解析品类字典 key 时不再省略品类条件匹配，避免命中同品牌型号的其它品类价格。
- 售价编辑改用 `LambdaUpdateWrapper.set()`，支持清空备注（原 `setXxx(null)+updateById` 会静默保留旧备注）。
- 异步/同步导出表头统一为 31 列；SCM 退货负数分录继承标准价/特批文件/支付方式。
- 新增 3 个实体补入 `sql/ops_entity_config_seed.sql`，满足实体自动注册要求。

## 改进建议（非阻塞）

- 文件上传的扩展名/MIME/文件名清理在 `BusinessSpecialFileServiceImpl`、`PaymentQrServiceImpl`、`FileUploadController` 间重复，建议抽公共 `UploadFileUtil`，避免安全修补遗漏。
- 运营商/组织/sso 令牌守卫在 `ProductPriceController`、`AdminPaymentQrController`、`EmployeeController`、`EmployeeBusinessEntryServiceImpl` 间重复，建议收敛到 `OrgRoleService`/`JwtTokenInspector` 的单一方法。
- `CommissionRuleService.getCategories()` 未缓存，售价维护和未配置商品的查价会访问平台字典接口，建议改为带 Caffeine `dict` 缓存的字典服务方法。
- `PAYMENT_METHODS` 前后端各自硬编码，后续新增支付方式需双端发布，建议由字典或接口统一下发。
- 特批文件上传可复用 `BusinessVoucherUploader` 的 token resolver 与图片压缩逻辑，减少重复实现。
- 函数/组件大小超规范：`PaymentQrServiceImpl.upload`（62 行）、`BusinessSpecialFileServiceImpl.upload`（49 行）、`EmployeeBusinessEntryServiceImpl.validateProduct`（50 行）、`BusinessProductCard.vue`（约 307 行），建议后续拆分。
- 性能：逐产品查售价/特批文件为 N+1 查询；收款码每次请求全量哈希 + ImageIO 解码；导出每次启动 python3；H5 售价缓存 60s 且 Map 不清理；建议分别改为批量查询、按 fileHash 短缓存、进程内 XLSX 写入、过期淘汰。
- 收款码上传并发（双管理员/双击）时文件替换与哈希登记可能短暂不一致；当前不一致会拒绝展示（fail-safe），建议上传串行化或行锁。
- `ProductItem.isSpecial` 后端已不读取，建议从前端载荷/DTO 删除；订单/明细双写支付方式、明细冗余特批 URL/名称为有意取舍，后续如需单一数据源可改为仅存 ID 查询。
- “低于标准价”判定在前端校验/组件 hook/后端各有一份，建议抽共享 predicate（后端保留独立校验防绕过）。
- `ScmBaseDataClient` 超过 50 个组织时整表 `cache.clear()`，建议改为按过期/最旧淘汰。

## 部署顺序与风险

1. 备份 `mall_db` / `ai_platform`。
2. 执行 `sql/migrate_product_price_payment_qr.sql`（**必须先于新 ops JAR**）。
3. 执行更新后的 `sql/ops_entity_config_seed.sql`（新增产品售价/特批文件/收款码配置 3 个实体注册）。
4. 发布新 ops 后端 JAR。
5. 发布平台主站前端（`html/platform/`）。
6. 在 `ai_platform` 执行 `doc/add_product_price_menu.sql`。
7. host nginx 增加 `/ops/product-price` 白名单到 `172.17.0.1:9081` 并 reload；否则刷新会落到 Ops H5。
8. 发布员工 H5（`html/ops/`，先清 assets）。
9. 设置 `PAYMENT_QR_BASE_DIR` 指向持久卷（默认 `${user.home}/data/payment-qr`），避免容器重建丢失收款码。
10. 平台后台上传收款码，并完成核心商品售价配置后再放开员工制单。

**风险**：未配置售价的存量商品上线后会被阻止制单，需提前批量配置；`ops_product_price` 唯一键为 `(corp_id, product_id)`，逻辑删除后重新新增走恢复逻辑，不能直接 INSERT；平台主站发布前确认 `ai-native-platform` 工作区中既有的组织创建改动不被混入本功能提交。
