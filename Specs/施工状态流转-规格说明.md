# 业务订单施工状态流转规格（派工 → 施工中）

> 状态：施工状态链与客户签字组件升级均已发布生产（2026-11-23）；真实施工员 E2E 待现场复测  
> 范围：公众号员工工作台（ops H5）+ ops 后端 + 底座工作流 + 平台主站 PC  
> 目标：派工指派施工员后不再直接「施工中」，施工员确认接收、上门打卡、客户手写签字确认、确认开工后才进入「施工中」。

---

## 1. 背景与问题

原流程「派工出库」节点审批通过后，工作流直接进入「施工中」节点并把
`ops_business_order.biz_status` 置为 `4`。此时施工员可能尚未看到任务、尚未到场、
客户毫不知情，导致进度失真、客户纠纷无凭证、施工责任界定不清。

本次在「派工」与「施工中」之间新增业务状态链，每一步留痕（操作人、时间、定位、
现场照片、客户签字），并保持既有工作流、完工验收（经办人审批）、外部施工员、
组织切换等规则不变。

---

## 2. 状态定义

持久化字段：`ops_business_order.biz_status VARCHAR(32)`，中文名来自字典
`business_order_status`。**「施工中」沿用历史 key `4`**，历史数据零迁移。

| 状态码（持久化） | 名称 | 含义 |
|---|---|---|
| `WAIT_ACCEPT` | 待接收 | 已指派施工员，等待确认接单 |
| `ACCEPTED` | 已接收 | 施工员已确认接单，待上门 |
| `ARRIVED` | 已上门 | 已到场打卡（定位/照片/备注） |
| `CUSTOMER_CONFIRMED` | 客户已确认 | 客户已签署用户告知书 |
| `CUSTOMER_REFUSED` | 客户拒绝确认 | 异常状态，通知派工人/运营介入 |
| `4` | 施工中 | 已确认开工（含义收窄） |
| `5` / `6` / `7` | 施工完成 / 完工验收 / 历史归档 | 既有状态，不变 |

其他既有 key（`-1`、`0`、`1`、`2`、`3`）不变。

## 3. 状态流转矩阵

| 当前状态 | 操作 | 目标状态 | 操作人 | 服务端接口 |
|---|---|---|---|---|
| `3` 派工出库 | 指派施工员（工作流节点动作） | `WAIT_ACCEPT` | 派工员 | 工作流 `OPS_DISPATCH_OUTBOUND` |
| `WAIT_ACCEPT` | 确认接收 | `ACCEPTED` | 施工员 | `POST .../construct/accept` |
| `WAIT_ACCEPT` | 拒绝接单（≥5字） | `3` 派工出库（回退） | 施工员 | `POST .../construct/reject` |
| `ACCEPTED` | 上门打卡 | `ARRIVED` | 施工员 | `POST .../construct/arrive` |
| `ARRIVED` | 客户签字确认 | `CUSTOMER_CONFIRMED` | 施工员（客户在场） | `POST .../construct/customer-confirm` |
| `CUSTOMER_REFUSED` | 客户回心转意后重新签字 | `CUSTOMER_CONFIRMED` | 施工员 | 同上（恢复路径） |
| `CUSTOMER_CONFIRMED` | 重新签字（版本+1） | `CUSTOMER_CONFIRMED` | 施工员 | 同上 |
| `ARRIVED` | 客户拒绝确认（≥5字） | `CUSTOMER_REFUSED` | 施工员 | `POST .../construct/customer-refuse` |
| `CUSTOMER_CONFIRMED` | 确认开工 | `4` 施工中 | 施工员 | `POST .../construct/start` |
| `4` / `5` | 提交施工记录（工作流节点动作） | `5` 施工完成 | 施工员 | 工作流 `OPS_CONSTRUCTION_RECORD` |

任何不在矩阵内的流转返回 `INVALID_STATUS_TRANSITION`。

### 文字版流转图

```
派工出库(3) ──指派施工员──▶ 待接收(WAIT_ACCEPT)
   ▲                              │ 确认接收
   │ 拒绝接单(≥5字)               ▼
   └──────────────────────── 已接收(ACCEPTED)
                                  │ 上门打卡(定位+照片)
                                  ▼
                              已上门(ARRIVED)
                            ┌─────┴─────┐
                   客户签字 │           │ 客户拒绝
                            ▼           ▼
                   客户已确认(CUSTOMER_CONFIRMED)   客户拒绝确认(CUSTOMER_REFUSED)
                            │ 确认开工        │ 客户同意后重新签字
                            ▼                └──▶ 客户已确认
                      施工中(4) ──施工记录──▶ 施工完成(5) ──完工验收(6)──▶ 归档(7)
```

### 异常分支

- **拒绝接单**：订单退回 `3` 派工出库，清空施工员与各节点时间；工作流任务驳回
  并按 `PREVIOUS` 退回派工节点，重新生成派工待办（派工人收到待办消息）。
- **客户拒绝确认**：订单进入 `CUSTOMER_REFUSED`，任务仍停留在施工执行节点；
  通知派工人/经办人。客户同意后可重新签字恢复；运营可在异常中心介入。
- **超时未接收**：本期不实现自动回退；可在工作流超时扫描/运营异常中心扩展。

## 4. 与既有体系的兼容

| 体系 | 处理 |
|---|---|
| 工作流 | 派工任务仍复用工作流待办；接收/打卡/签字/开工是业务操作，不新增审批节点。「施工执行」节点 `biz_status` 置空，不再进入即写「施工中」 |
| 施工记录 | 节点动作强校验 `biz_status ∈ {4,5}`，未开工不可提交，防止绕过 |
| 完工验收 | 不变；验收不通过退回「施工完成」节点（`biz_status=5`），允许重新提交施工记录 |
| 外部施工员 | 规则不变；外部用户仅公众号工作台操作，全流程可用 |
| 组织切换 | 写操作要求当前组织 = 订单组织；待办仍按用户过滤 |
| 入户随访（VISIT） | 保持旧口径：派工后直接 `4` 施工中，不进入确认链（无施工/客户告知书语义） |
| 存量数据 | **不回退**：存量 `4` 订单视为已开工，继续原流程；分布核查 SQL 见迁移脚本末尾 |

## 5. 数据模型

迁移脚本：`sql/migration_business_order_construct_flow.sql`（mall_db + ai_platform）
回滚脚本：`sql/migration_business_order_construct_flow_rollback.sql`

### 5.1 订单表新增

| 字段 | 类型 | 说明 |
|---|---|---|
| `worker_id` / `worker_name` / `worker_user_type` | BIGINT / VARCHAR(50) / TINYINT | 指派施工员 |
| `dispatch_task_id` | BIGINT | 最近一次派工任务ID（SCM 按 dispatchId 幂等重试） |
| `accept_time` / `arrive_time` / `customer_confirm_time` / `start_time` | DATETIME | 关键时间点 |
| `version` | INT DEFAULT 0 | 乐观锁（应用层 CAS，不启用 @Version 拦截器） |

`biz_status` 扩为 `VARCHAR(32)`；`ops_business_flow_record.biz_status`、
`ops_business_refund.original_biz_status` 同步扩容。

### 5.2 施工流转日志 `ops_order_construct_log`

`order_id / order_no / from_status / to_status / action / operator_id / operator_name /
operator_type / operate_time / location_lng / location_lat / location_address /
location_status / attachment_ids / notice_id / remark` + BaseEntity 基础字段。

`action`：`ASSIGN / ACCEPT / REJECT / ARRIVE / CUSTOMER_CONFIRM / CUSTOMER_REFUSE / START`。

> 命名说明：项目规范要求 ops 自有表使用 `ops_` 前缀（`biz_` 仅用于跨子系统共享表），
> 因此任务书中的 `biz_order_construct_log` / `biz_customer_notice` 落地为
> `ops_order_construct_log` / `ops_customer_notice`。

### 5.3 客户告知书 `ops_customer_notice`

`order_id / order_no / worker_id / worker_name / customer_name / notice_content（内容快照）/
notice_time / sign_image_url / sign_image_hash（SHA-256）/ sign_time /
sign_location_lng / sign_location_lat / version / status / pdf_url` + BaseEntity 基础字段。

唯一键 `uk_order_version(order_id, version)`；重签时旧版本 `status=0` 保留。

### 5.4 派工出库幂等与重新派工（关键）

- **同任务重试**：`dispatch_task_id` 在调用 SCM 前先落库；SCM `from-dispatch`
  按 `dispatchId=taskId` 幂等，重试返回同一张出库单（含物料领用草稿），不会重复出库。
- **拒绝接单后重新派工**：货物已实际出库，**复用原销售出库单与物料领用草稿**，
  不再调用 SCM 建单（避免“已产生出库单，不可重复派工”导致永久卡单）。
  重新派工只更新施工员/期望上门时间并写新的 ASSIGN 日志。
- **其他来源的重复派工**：已有出库单且既非同一任务重试、也非拒绝后重新派工 → 拦截。
- **工作流节点**：节点 5 强制 `return_mode=PREVIOUS`、`return_biz_status=3`，
  拒绝接单必须退回派工节点重建派工待办，而非终止实例。

### 5.5 状态字典

`sys_dict_item` 新增 `WAIT_ACCEPT / ACCEPTED / ARRIVED / CUSTOMER_CONFIRMED /
CUSTOMER_REFUSED`，`item_order` 重排到 `3` 与 `4` 之间；施工中仍为 key `4`。

> 字典有 Caffeine 缓存：迁移后重启 platform（或等待 TTL），ops 状态名缓存 5 分钟。

## 6. 后端接口

基路径：`/api/ops/employee/business-data/orders/{orderId}/construct`
（`/api/ops/employee/**` 对内部/外部员工均开放；会员 SSO 令牌拒绝）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 施工视图：状态、权限、时间线、告知书、内容预览 |
| GET | `/logs` | 流转时间线 |
| GET | `/notice` | 当前告知书 + 历史版本 + 内容预览 |
| POST | `/accept` | 确认接收 |
| POST | `/reject` | 拒绝接单 `{reason}`（≥5字） |
| POST | `/arrive` | 上门打卡 `{locationStatus,lng,lat,address,attachmentIds,remark}` |
| POST | `/customer-confirm` | 客户签字 `{signImageBase64}`（可带定位） |
| POST | `/customer-refuse` | 客户拒绝 `{reason}`（≥5字） |
| POST | `/start` | 确认开工 |

内部接口（platform，`X-Internal-Token`）：

- `POST /api/internal/wf/task/reject` — 施工员拒绝接单时由 ops 代为驳回任务；
  平台 `requireTaskOwner` 二次校验处理人，formData 为空不触发节点动作。
- `POST /api/internal/wf/notify` — 施工进度公众号通知（尽力而为）。

### 错误码

| 错误码 | 文案 |
|---|---|
| `INVALID_STATUS_TRANSITION` | 当前状态不允许此操作，请刷新后重试 |
| `NOT_ORDER_WORKER` | 您不是该订单的施工员，无权操作 |
| `ORDER_STATUS_CHANGED` | 订单状态已变更/流程已结束，请刷新 |
| `ARRIVE_BEFORE_ACCEPT` | 未接收任务/未完成打卡，无法执行 |
| `LOCATION_REQUIRED` | 请允许定位权限后重试，或手动填写地址 |
| `SIGN_IMAGE_REQUIRED` | 请客户完成手写签字 |
| `CUSTOMER_NOTICE_REQUIRED` | 客户尚未签署用户告知书，无法开工 |
| `REJECT_REASON_REQUIRED` / `CUSTOMER_REFUSE_REASON_REQUIRED` | 原因不少于5字 |

## 7. 安全、并发与幂等

1. **身份**：当前员工必须 = `worker_id`（或历史订单的施工执行待办处理人），
   且当前组织 = 订单组织；派工人/经办人/运营只读。
2. **状态强校验**：服务端状态机 + `biz_status`/`version` CAS；前端按钮隐藏不作为保障。
3. **并发**：`SELECT ... FOR UPDATE` 行锁串行化同一订单（跨实例有效），
   提交时再带 `biz_status + version` 双重条件，0 行返回 `ORDER_STATUS_CHANGED`。
4. **幂等**：已接收/已打卡/已开工/客户拒绝重复提交返回首次结果；客户签字按
   图片 SHA-256 判重，重复文件立即清理，不产生重复日志。
5. **开工前置**：必须存在 `ARRIVE` 日志 + 有效告知书（`status=1` 且签字 URL 非空）。
6. **签字凭证**：PNG 魔数校验、≤2MB、SHA-256 入库、内容快照入库、版本化保留。
7. **定位隐私**：定位仅用于施工凭证；告知书/日志接口需员工身份，签字图片 URL
   为不可猜测 UUID 路径（与既有业务附件同一存储策略）。
8. **审计**：每步写 `ops_order_construct_log`；接口另挂 `@OperationLog`。

## 10. 部署顺序

1. 备份数据库与当前 JAR/前端包。
2. 执行 `sql/migration_business_order_construct_flow.sql`（mall_db + ai_platform）。
3. 执行 `doc/migration_workflow_construct_notify.sql`（ai_platform）。
4. 发布 platform JAR（新增内部接口/通知场景）+ 重启（清字典缓存）。
5. 发布 ops JAR。
6. 发布 ops H5（`npm run build:h5`，`rm -rf assets/*` 后上传）+ 主站前端（若含 PC 状态颜色）。
7. （可选）执行 `ops_entity_config_seed.sql` 注册两个新实体。
8. 冒烟：派工 → 施工员确认接收 → 打卡 → 客户签字 → 确认开工 → 施工记录 → 完工验收。

回滚：先回滚 ops/platform JAR 与前端，再执行
`sql/migration_business_order_construct_flow_rollback.sql`（默认只停用字典项/恢复节点，
新表与历史凭证保留）。

## 12. 风险与遗留

| 风险 | 处理 |
|---|---|
| 施工员长期不接单卡单 | 本期不自动回退；可配置工作流超时扫描/运营异常中心处理 |
| 客户拒绝确认 | 进入 `CUSTOMER_REFUSED`，通知派工人/运营；客户同意后可重签 |
| 手写签字法律效力 | 内容快照 + 签字图片 + SHA-256 + 时间/定位/操作人；建议后续补 PDF 归档与可信时间戳 |
| PDF 未生成 | 需引入 iText/OpenPDF 依赖（当前离线仓库无）；`pdf_url` 已预留，前端可打印 |
