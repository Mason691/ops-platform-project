# 业务数据主子表拆分 — 规格说明

> 状态：代码已实施（2026-11-11），生产迁移/E2E 待执行
> 关联需求：ops_business_data 单表 → 订单头 + 商品分录主从结构，并新增退货。

## 1. 功能概述

将增值业务“业务数据”由单表 `ops_business_data` 拆分为：

| 表 | 角色 | 粒度 |
|---|---|---|
| `ops_business_order` | 订单头（主表） | 一条业务订单一行 |
| `ops_business_order_item` | 商品分录（子表） | 商品 × 经办人一行（保留原明细粒度） |
| `ops_business_data` | 兼容视图 | 指向子表的简单视图，供 SCM / AI / 旧 JAR 只读 |

同时新增退货申请与审批：子表记录 `is_return / return_quantity / return_amount /
settle_quantity / return_status / original_receipt_amount`，审批通过后按实际结算数量
调整收款金额与提成，并回写主表合计。

## 2. 表结构

### 2.1 主表 `ops_business_order`

订单级公共字段：`corp_id, order_key, batch_no, order_no, business_group_no,
receipt_no, company, customer, customer_phone, platform_member_id, community_id,
community_name, detailed_address, agent_names, agent_phones, receipt_date,
finance_receipt_date, fund_dynamic_rows, is_received, voucher_url, total_amount,
total_commission, calc_status, finance_check_*` + BaseEntity 审计字段。

- `order_key`：幂等迁移与订单唯一标识。手工/导入新单为 `O|{order_no}`；历史数据为
  `O|order_no` → `G|business_group_no` → `R|receipt_no|batch_no|customer_phone` → `I|id`。
- 唯一键 `(corp_id, order_key)`；`order_no / receipt_no / batch_no / calc_status` 建索引。
- `total_amount` 按“订单内 品类+品牌+型号+单价”去重后求和，避免多经办人重复计额。

### 2.2 子表 `ops_business_order_item`

原 `ops_business_data` 全部列 + 新增：

| 列 | 类型 | 说明 |
|---|---|---|
| `order_id` | BIGINT | 主表外键 |
| `is_return` | VARCHAR(2) | 是否退货（是/否） |
| `return_quantity` | INT | 累计退货数量 |
| `return_amount` | DECIMAL(12,2) | 累计退货金额 = 退货数量 × 销售单价 |
| `settle_quantity` | INT | 实际结算数量 = 销售数量 - 退货数量 |
| `return_status` | VARCHAR(20) | 未申请/审批中/已通过/已驳回 |
| `original_receipt_amount` | DECIMAL(12,2) | 退货前收款金额（首次退货时留存） |

退货审批通过后：`receipt_amount = 销售单价 × settle_quantity`，因此所有既有
SUM/MAX 统计自动切换为结算口径；导出额外展示原值、退货信息与结算数量。

### 2.3 退货申请表 `ops_business_return`

按“商品分录”申请，同一订单同产品（品类+品牌+型号+单价）的全部经办人行一起调整：
`corp_id, order_id, item_id, product_key, return_quantity, return_amount, reason,
status(审批中/已通过/已驳回), applicant_*, approver_*, approve_time, approve_remark` +
BaseEntity。

## 3. 迁移与回滚

脚本：`sql/migrate_business_order_split.sql`

1. 备份 `ops_business_data`（脚本头部给出命令，执行人手动确认）。
2. 建主表、退货表；将 `ops_business_data` 重命名为 `ops_business_order_item`。
3. 子表加列/索引；创建兼容视图 `ops_business_data`。
4. 按 order_key 聚合回填主表；回填子表 `order_id`；退货字段初始化。
5. 幂等：主表按 `(corp_id, order_key)` NOT EXISTS；DDL 走 information_schema。

回滚：`sql/rollback_business_order_split.sql`（删视图 → 子表改回原名 → 删新表与新增列）。
执行顺序：**停 ops 后端 → 备份 → 迁移 → 启动新 JAR**；SCM 只读视图无需停。

## 4. 功能改造

- **导入**：按 收据号+批次公司+客户手机 归组建主表，产品×经办人写入子表；
  订单编号沿用 `{dd}+3位全局流水`；结果按主表/子表条数分别反馈。
- **员工手工新增**：一次提交建 1 主表 + N（产品×经办人）子表，共享订单编号。
- **提成计算**：以子表为输入，规则不变；退货行按 `settle_quantity/sale_quantity`
  等比缩放提成；计算后同步主表 `calc_status/total_commission`。
- **财务核对**：订单级字段更新主表，并同步订单全部子表；已上报集团拒绝。
- **退货**：经办人/财务发起 → 审批通过 → 更新同产品全部子行 → 主表重算 → 订单提成重算；
  驳回不变更业务数据；累计退货不得超过销售数量；已上报集团不可退货。
- **列表**：订单主行 + 可展开商品明细，明细增加退货字段；订单按 `order_id` 聚合。
- **导出**：平铺格式追加 是否退货 / 退货数量 / 实际结算数量 三列。
- **下游**：作战地图、品类提成汇总、员工业绩、会员台账继续读子表；因
  `receipt_amount` 已改为结算金额，口径自动一致，聚合 SQL 无需改去重规则。

## 5. 验收标准

1. 迁移后主表条数 = 去重订单数；子表条数 = 原明细条数；合计金额与原去重口径一致。
2. 导入 2 产品 × 2 经办人 → 1 主表 + 4 子表，订单编号一致，主表合计正确。
3. 提成结果与拆分前一致；无退货时金额零差异。
4. 财务核对更新后，列表/导出/统计同步。
5. 退货审批通过：子表结算数量/金额/提成正确，主表合计同步；已上报订单拒绝。
6. 导出字段完整，主从一致。

## 6. 部署顺序（生产）

1. **备份** `ops_business_data`（脚本头部命令）。
2. **停 ops 后端**（必须；旧 JAR 写入经兼容视图，不会维护主表）。
3. 执行 `sql/migrate_business_order_split.sql`（`mysql --default-character-set=utf8mb4`）。
4. 启动新 ops JAR（`docker compose up -d ops-backend`）。
5. SCM 无需改代码/重启（`ops_business_data` 视图保持原列）。
6. 发布平台主站前端（`views/biz/BusinessData.vue` + 两个退货弹窗）与 ops H5。
7. 验证：导入 2 产品×2 经办人 → 1 主表 + 4 子表；`GET /api/ops/admin/business-data/reconcile` 返回 0 差异；SCM 业务数据选择器可正常查询。
8. 回滚：停 ops 后端 → `sql/rollback_business_order_split.sql` → 部署旧 JAR（退货数据会丢失）。
