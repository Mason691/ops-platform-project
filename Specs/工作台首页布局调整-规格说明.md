# 员工工作台首页布局调整 规格说明

> 状态：✅ 已实现并部署（2026-11-18，生产 ops H5）
> 关联页面：`frontend/src/pages/employee/dashboard.vue`（员工工作台，H5 `/ops/`）
> 关联接口：`GET /api/wf/task/todo`、`GET /api/wf/log/my`（均复用，未新增后端接口）
> 日期：2026-11-18

## 一、功能概述

调整公众号员工工作台首页的信息优先级，让员工进入工作台后先「开展业务」与「处理待办」：

1. 首页新增「新增业务」主按钮（主色、居中、视觉权重最高）；
2. 待办任务从「常用功能」二级入口提升为首页主卡片，最多展示 5 条，超出显示「查看更多（共 N 条）」；
3. 工作业务日志不单独展示，改为「常用功能」中的菜单入口（2026-11-18 调整）；
4. 其余模块（个人信息、年度统计、常用功能、组织切换、底部 Tab）位置与能力保持不变。

> 说明：需求原文假设技术栈为 Vue3 + Element Plus + qiankun、路由 `/workbench/*`。
> 实际工程为 uni-app（H5 + mp-weixin），工作台是 `pages/employee/dashboard`，
> 待办/日志由底座工作流接口提供。本规格按真实工程落地，交互语义保持一致。

## 三、用户故事

1. 作为业务员工，我进入工作台后第一眼能看到大号「新增业务」按钮，一键进入制单页。
2. 作为审批人，我在首页直接看到最多 5 条待办，含业务类型、标题、节点、发起人、到达时间、剩余时限和超时/临期标识。
3. 作为审批人，待办超过 5 条时我能看到「查看更多（共 N 条）」并进入完整列表。
4. 作为员工，我能从「常用功能 → 工作业务日志」进入完整的业务日志列表。
5. 作为多组织员工，切换组织后待办与可发起业务类型刷新；日志列表进入时按当前登录人加载。

## 四、待办展示与排序规则

- **数量**：首页最多 5 条；`total > 展示条数` 时底部显示「查看更多（共 N 条）」。
- **紧急度**（基于底座 `remainingHours`，24h SLA）：
  - `≤ 0` → 已超时（红色色条 + 「已超时」标签）
  - `0 < 剩余 ≤ 6h` → 临期（橙色色条 + 「临期」标签）
  - 其余 → 普通（灰色文案）
- **排序**：超时 > 临期 > 普通；同级别按到达时间（`task.createTime`）倒序，最后按任务 ID 倒序。
  - 底座 `pageTodo` 只按创建时间倒序且无排序参数；跨仓库改平台后端不在本次范围，
    因此排序在 H5 侧 `utils/workflowTodo.js` 统一完成，**首页与完整待办列表页共用同一函数**。
- **过滤**：沿用既有「未收齐全款的派工待办不展示」规则，首页与列表页共用 `filterIneligibleDispatch`。
- **时限刷新**：加载时把 `remainingHours` 固化为本地截止时刻，之后每 60s 重算文案；
  页面重新可见时重新拉取校准。运行中不重排，避免卡片跳动误触。

## 五、新增业务按钮

- 位置：年度统计下方、待办卡片上方，左右各留 24rpx，高度 96rpx（≥44px 点击区）。
- 文案：单业务类型时取类型的 `action`（当前为「新增业务」）；多类型时默认「新增业务」。
- 交互：单类型直接 `navigateTo` 新增页；多类型弹出底部弹层（复用 `BottomSheetSelect`）。
- 无权限策略：组织 `permissions` 为空时**隐藏**按钮（与「常用功能」同口径），不展示死按钮。
- 当前注册表仅 `OPS_BUSINESS_ORDER → /pages/employee/business-data-new`，后续新增类型只改 `useBusinessTypes.js`。

## 六、数据契约（全部复用既有接口）

### 6.1 待办

`GET /api/wf/task/todo?pageNum=1&pageSize=50`

| 返回字段 | 首页用途 |
|---|---|
| `total` | 「共 N 条」；已取回全量时改用过滤后条数，避免被隐藏的派工任务虚增 |
| `records[].task.id / instanceId` | 跳转 `/pages/employee/flow-task` |
| `records[].task.nodeName` | 当前节点 |
| `records[].task.createTime` | 到达时间（展示 + 排序） |
| `records[].businessType` | 业务类型标签（本地映射表） |
| `records[].businessSummary / businessId` | 标题 |
| `records[].initiatorName` | 发起人 |
| `records[].remainingHours` | 剩余时限基准（无 `remainSeconds/overdue` 字段） |

> 未新增 `/api/workbench/todo/summary`：现有接口已含首页所需全部字段，新增聚合接口无收益。

### 6.2 业务日志

工作台首页不再请求日志接口；「常用功能 → 工作业务日志」进入既有列表页，
由 `/pages/employee/work-log` 继续调用 `GET /api/wf/log/my`（分页、筛选），
接口与页面均未改动。

> 未新增 `/api/workbench/business-log/summary`：首页不展示日志摘要，无需聚合接口。

### 6.3 可发起业务类型

未新增 `/api/workbench/business-types`：H5 只有「业务数据订单」一个新增入口，
新增仅返回单条记录的接口属于过度设计；改为前端注册表，结构保持
`{ code, name, action, route }`，后续可平滑替换为接口。

### 6.4 错误与降级

- 待办失败：卡片内展示错误 + 重试，不影响统计/菜单。
- 派工资格查询失败：fail-open（保留任务），由任务页与后端最终拦截。

## 七、组织切换与并发

- `dashboard.onOrgChanged` 重新加载待办卡；新增业务按钮随 `noPermissionTip` 显隐。
- 待办 Hook 用递增 `requestSeq` 丢弃过期响应（`uni.request` 不支持取消），避免旧组织数据覆盖新组织。
- 页面 `onShow` 回到工作台时静默刷新待办卡；首次进入由组件 `mounted` 加载，不重复请求。

## 八、不改变的能力

- 工作流审批逻辑、任务详情页、待办完整列表页、日志列表/详情页均不改动（列表页仅共享排序/过滤口径）。
- 业务日志无手工「记录日志」入口（日志由审批/业务动作自动生成），入口改为菜单卡片不丢失任何能力。
- 组织切换、底部 Tab、AI 助手、个人中心等不受影响。

## 十、风险与后续

1. **排序一致性**：平台后端未提供优先级排序参数，H5 双端共用排序函数保证一致；
   若后续底座支持 `sortBy=urgency`，应删除前端排序并直接透传。
2. **时限精度**：`remainingHours` 为小时级且 24h SLA 封顶，超时只能显示「已超时」无法给出超时时长。
3. **条数上限**：列表与首页都只拉 50 条，待办超过 50 时「共 N 条」为后端 total（可能包含被隐藏的派工任务）。
4. **埋点**：项目无行为分析服务，`utils/track.js` 统一出口当前仅开发环境打印，生产静默。
