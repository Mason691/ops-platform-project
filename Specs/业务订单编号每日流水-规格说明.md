# 业务订单编号（dd + 每日流水）— 规格说明

> 状态：✅ 已发布生产（2026-11-18 20:51）并完成编号冒烟；规格见第七节发布记录
> 范围：增值业务 → 业务数据订单（员工手工制单 + Excel 导入）订单编号生成与查询/统计口径

## 一、编号规则

- 格式：`dd` + 3 位流水，例：2026-11-18 第 1 单 → `18001`，第 613 单 → `18613`。
- `dd`：订单创建日期的“日”，两位（01~31），时区固定 `Asia/Shanghai`。
- 流水：从 `001` 起每日归零；计数主体是**订单**，一个订单（含多商品、多经办人、多条明细）只占一个号。
- 溢出：当日第 1000 单起自动进位为 4 位（`181000`），不阻断下单；`order_no` 列 `VARCHAR(20)` 可容纳。
- 编号只由后端生成（`OrderNoGenerator`），前端请求 DTO 无订单编号字段；退回草稿编辑重提沿用原编号，不重新占号。

## 二、计数域与时间

- 计数域：`operator_corp_id` = 订单归属组织的运营商（城市合伙人 → `parent_corp_id`，运营商 → 自身）。
  同一运营商及其全部下属城市合伙人共用一个序列；不同运营商互不影响。
- 解析运营商走平台内部接口（`OrgRoleService`），查询失败/城市合伙人缺少上级时**拒绝生成并回滚订单**，不允许退回本地计数（否则会重号）。
- 日期以 `Asia/Shanghai` 计算；容器 `TZ=Asia/Shanghai`。

## 三、并发与唯一性

- 存储：新表 `ops_order_daily_sequence(operator_corp_id, seq_date, last_seq)`，主键 `(operator_corp_id, seq_date)`。
- 原子自增 SQL：
  `INSERT ... VALUES (?, ?, LAST_INSERT_ID(1)) ON DUPLICATE KEY UPDATE last_seq = LAST_INSERT_ID(last_seq + 1)`，
  同一连接 `SELECT LAST_INSERT_ID()` 取号；`REQUIRES_NEW` 独立事务，避免导入长事务长期持有流水行锁。
- 唯一性方案（需求三选 A）：`order_no` 作为展示编号，允许跨月同日重复；
  数据库唯一性由 `ops_business_order.order_key` 保证，新格式 `O|yyyyMMdd|orderNo`（`uk_corp_order_key(corp_id, order_key)`）。
- 列表/统计按 `order_id` 分组（优先），历史无 `order_id` 行回退到订单编号/业务组号/收据号；
  跨月同号可通过创建时间区分。
- 已知取舍：`REQUIRES_NEW` 在订单保存失败/回滚时可能留下号段空洞（编号唯一但不保证绝对连续）；
  正常成功提交的并发取号连续、无重复。

## 四、迁移与上线

1. `mall_db` 执行 `sql/migrate_order_no_daily_sequence.sql`：建表 + 按“运营商树”回填**当天**各运营商已用的最大流水。
2. 上线顺序：先停止旧 ops 容器（避免迁移后旧 JAR 继续占用全局号）→ 执行迁移 → 启动新 JAR。
   若迁移与切换之间仍有旧单，新序号可能从回填值开始，唯一键兜底并提示重试。
3. 旧表 `ops_order_sequence` 不再被代码读取，保留用于回滚，不删除。
   回滚旧 JAR 前必须把 `ops_order_sequence.last_seq` 提升到当天所有运营商
   `last_seq` 的最大值，否则旧全局号会与本日新号重复：
   `UPDATE ops_order_sequence SET last_seq = GREATEST(last_seq,
   (SELECT COALESCE(MAX(last_seq),0) FROM ops_order_daily_sequence WHERE seq_date = CURDATE())) WHERE id = 1;`
   能回滚则优先回滚，不能回滚时优先向前修复。

## 五、查询与展示

- 平台列表“订单编号 / 收据号”列展示 `dd+流水`，旁边保留创建时间列；
  H5 订单列表展示订单编号 + 收款日期/创建时间。
- 平台/H5 列表的订单编号筛选改为模糊匹配（`LIKE %关键词%`），精确输入仍命中。
- 导出沿用订单编号字段，自动按新规则输出。

## 六、验证

1. 并发 50 次取号唯一且连续（临时表压测）。
2. 同一运营商下不同 corp 的订单共享序列；不同运营商各自从 001 开始。
3. 次日首单为 `dd001`；当日 1000 单进位 4 位不报错。
4. 一单多商品/多经办人只占一个号，明细共享 `order_no`。
5. 退回草稿重新提交订单编号不变。
6. 跨月同日同号时，`order_key` 唯一、列表按 `order_id` 分组不合并、创建时间可区分。
