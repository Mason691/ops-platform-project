# 业务订单以旧换新 — 规格说明

> 状态：已实施并部署生产（2026-11-17 19:21-19:24），迁移已执行；登录态业务端到端与微信真机待验证。
> 关联需求：公众号 H5 员工工作台「业务数据订单」新增订单支持以旧换新，保存后自动生成未审核 SCM 采购单，施工完成节点提示旧品入库。

## 1. 功能概述

- 商品明细每个商品行可选择「是否以旧换新」，选择「是」后录入抵扣金额与多件旧品。
- 商品行合计 = 销售单价 × 销售数量 − 抵扣金额；订单应付合计 = 各商品行合计之和。
- 订单保存成功后，按旧品明细自动生成一张 SCM 未审核采购草稿单（来源类型 `BUSINESS_ORDER_TRADE_IN`）。
- 业务状态到「5 施工完成」后，在订单详情与流程节点页提示旧品入库，直至 SCM 入库状态为 `ALL`。

## 2. 用户故事

1. 作为员工，我可以在商品卡上点选“是否以旧换新”，默认“否”，开启后录入抵扣金额和多件旧品。
2. 作为员工，我选择 SCM 商品库旧品时品牌/型号自动带出且不可篡改；也可选择“其他旧品”手工填写名称/品牌/型号。
3. 作为员工，我实时看到每行销售金额、抵扣金额、抵扣后金额，以及底部商品合计/抵扣合计/应付合计。
4. 作为员工，提交后能看到是否已生成旧品采购单；生成失败时能看到明确提示并在订单详情重试。
5. 作为施工/验收人员，我在施工完成节点能看到旧品入库提醒与旧品汇总，并跳转关联采购单。
6. 作为采购人员，我在 PC 端完善供应商/仓库/单价；其他旧品必须选择真实入库商品后才能提交/审核。

## 3. 验收标准

- [x] 「是/否」分段选择器，默认否；否时抵扣与旧品区收起并按 0/空处理。
- [x] 抵扣金额必填、>0、最多两位小数、不得超过该行销售金额；错误提示“抵扣金额不能超过商品金额”。
- [x] 旧品至少 1 件；每件商品与数量必填，数量为正整数；每行最多 50 件、全单最多 100 行。
- [x] 后端重新计算并落库，不信任前端金额；`receipt_amount` 仍为销售额，提成基数不变；新增抵扣后金额字段。
- [x] 订单保存后自动生成一张未审核 SCM 采购单，来源订单号/明细（名称、品牌、型号、数量、备注）一致。
- [x] 同一业务订单重复提交/重试不重复生成采购单（SCM 唯一键 + 幂等返回）。
- [x] 采购单生成失败时业务订单不静默：成功页提示、订单详情/流程节点提示，经办人可重试。
- [x] 施工完成（业务状态 5）及施工记录/验收节点显示“本订单含以旧换新旧品，请及时办理旧品入库。”；非以旧换新不显示。
- [x] 旧品入库完成（SCM `inboundStatus=ALL`）后提醒变“旧品已入库”。
- [x] 订单详情/PC 业务数据页可查看关联采购单号与状态，PC 可跳转 SCM 采购订单。
- [x] 非以旧换新订单的制单、列表、导出、提成、财务核对逻辑保持原口径。

## 4. API

### 4.1 员工制单（新增字段）

`POST /api/ops/employee/business-data/manual`

`products[]` 新增：

```json
{
  "isTradeIn": true,
  "deductionAmount": 300.00,
  "tradeInItems": [
    {
      "productId": 123,
      "productName": "旧燃气灶",
      "brand": "美的",
      "model": "JZT-Q08",
      "category": "燃气灶",
      "quantity": 1,
      "unit": "台",
      "remark": "成色良好",
      "isManual": false
    }
  ]
}
```

### 4.2 重试自动采购单

`POST /api/ops/employee/business-data/orders/{orderId}/trade-in-purchase/retry`

- 员工 JWT；仅订单经办人可调用（`requireAgentOrder`）；SCM 侧幂等。
- 返回 `{ status: SUCCESS|FAILED, purchaseOrderId, billNo, error }`。

### 4.3 SCM 内部接口（X-Internal-Token）

- `POST /api/internal/scm/pur-order/trade-in`：创建未审采购草稿；同一 `(corp_id, BUSINESS_ORDER_TRADE_IN, businessOrderId)` 返回已有单据。
- `GET /api/internal/scm/pur-order/{id}/status?corpId=`：返回审批/审核/执行/入库状态。

## 5. 数据模型

### 5.1 ops

- `ops_business_order_item`：`is_trade_in VARCHAR(2) DEFAULT '否'`、`deduction_amount DECIMAL(12,2) DEFAULT 0`、`trade_in_payable_amount DECIMAL(12,2)`。
- `ops_business_order`：`has_trade_in`、`trade_in_deduction_amount`、`payable_amount`、`trade_in_purchase_status`、`trade_in_purchase_order_id`、`trade_in_purchase_bill_no`、`trade_in_purchase_error`。
- `ops_business_order_trade_in`：`corp_id, order_id, product_key, source_item_id, old_product_id, old_material_number, old_product_name, brand, model, category, quantity, unit, remark, is_manual` + BaseEntity 审计字段。
- 迁移：`sql/migrate_business_order_trade_in.sql`；实体注册：`sql/ops_entity_config_seed.sql`。

### 5.2 SCM

- `scm_pur_order`：`source_order_id BIGINT`，唯一键 `uk_pur_trade_in_source (corp_id, data_source, source_order_id)`。
- `scm_pur_order_entry`：`material_name, brand, model, unit_name, is_manual, source_trade_in_id, remark`。
- 迁移：`sql/migrate_pur_order_trade_in.sql`。

## 6. 金额与提成口径

| 口径 | 计算 |
|---|---|
| 行销售金额 `receipt_amount` | 销售单价 × 销售数量（原口径不变） |
| 行抵扣金额 `deduction_amount` | 用户录入，>0 且 ≤ 行销售金额 |
| 行抵扣后金额 `trade_in_payable_amount` | 行销售金额 − 行抵扣 |
| 订单应付 `payable_amount` | 订单销售合计 − 抵扣合计（按产品组 MAX 去重） |
| 提成 | 仍按 `receipt_amount`（销售额）计算，抵扣不冲减提成基数 |
| 定金/余款 | 以 `payable_amount` 为基数：余款 = 应付 − 定金 |

## 7. 多租户与安全

- `corp_id` 仅从 JWT 解析；旧品表含 `corp_id`，由 `TenantLineHandler` 自动过滤。
- 重试接口仅订单经办人（手机号匹配或创建人）可调用；员工令牌拒绝 `token_type=sso` 会员令牌。
- SCM 内部接口校验 `X-Internal-Token`，按请求 `corpId` 重建 SecurityContext；来源类型不允许通过公共创建/编辑接口手工切换。
- 选中 SCM 旧品时后端以商品资料为准，覆盖前端品牌/型号/名称，防篡改。
- 前端渲染旧品文本，不拼接 HTML。

## 8. 未覆盖/风险

- 以旧换新订单发生退货时的退款口径未单独改造（沿用原退货冲减逻辑），需业务确认。
- 其他旧品在 PC 端必须映射真实入库商品后才能提交/审核，否则无法生成入库单。
- 生产迁移必须先于 JAR 部署；本机无 3306/SCM 服务，端到端与微信真机验证未执行。
