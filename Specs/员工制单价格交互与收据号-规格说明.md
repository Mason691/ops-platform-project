# 员工制单价格交互与收据号 — 规格说明

> 状态：✅ 已实现并部署生产（2026-11-17 08:52）
> 入口：公众号 H5 → 员工登录 → 工作台 → 新增业务订单（4 步向导）

## 1. 功能概述

重构员工手工制单「商品明细」的价格交互与「收款信息」的凭证/收据号填报，并补齐财务核对环节的收据号留痕：

1. 商品型号选定后，销售单价以**价格卡片**展示，提供「修改单价」「恢复标准价」两个明确按钮；低价自动联动既有特批管控。
2. 收款二维码补齐加载/失败/校验失败三态与重试、点击放大；收款凭证增加“上传到账截图而非收据”的说明文案。
3. 「市场收款日期」后新增**收据号**（选填）字段，支持落库、字符集/长度校验与同组织查重提示。
4. 财务核对节点可修改/补录收据号，并在节点留痕中记录**修改前值 → 修改后值**（修改人/时间沿用工作流节点记录）。

## 2. 用户故事

- 作为经办人，我选择型号后能清楚看到当前单价、「修改单价」「恢复标准价」两个按钮，不需要猜文字链是否可以点击。
- 作为经办人，我把单价改低时自动展开特批文件与提成比例，并看到“低于标准价需上传特批文件”的就地提示。
- 作为经办人，我选二维码收款时能直接看到收款码，可点开放大；加载失败能重试，校验失败有明确提示。
- 作为经办人，我知道收款凭证应上传银行/支付渠道到账截图，而不是收据或白条。
- 作为经办人，我已取得收据号时可在制单阶段先填；未取得可留空，由财务核对时补录。
- 作为财务核对人员，我能看到并修改收据号，系统保留修改前后值供追溯；其他节点只读。

## 4. API 设计

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ops/employee/business-data/receipt-no/check?receiptNo=&customer=` | 制单失焦查重；返回 `{duplicate, message}`，同客户可复用 |
| POST | `/api/ops/employee/business-data/manual` | 新增 `receiptNo` 字段（选填），服务端二次校验字符集/长度/占用 |

### 保存请求新增字段

```json
{
  "receiptDate": "2026-11-17",
  "receiptNo": "0000376",
  "paymentMethod": "QR"
}
```

### 落库

- `ops_business_order.receipt_no`（订单头，制单阶段写入）
- `ops_business_order_item.receipt_no`（明细行，制单阶段同步写入，与财务核对/导入口径一致）
- 无 DDL 变更：两列均已存在，`idx_corp_receipt (corp_id, receipt_no)` 已建。

### 留痕

`ops_business_flow_record.result_json` 增加 `receiptNoBefore` / `receiptNoAfter`；平台主站订单详情「工作流处理留痕」在展开行展示「收据号变更：旧值 → 新值」。

## 5. 多租户与安全

- `corp_id` 仅从 JWT 解析；收据号查重固定按当前员工组织过滤。
- 会员 SSO 令牌（`token_type=sso`）不能调用收据号查重接口（返回 403）。
- 财务核对更新收据号沿用 `BusinessDataFinanceServiceImpl`：组织/状态校验 + 已上报集团拒绝。
- 收款码继续走员工鉴权接口 + 每次 SHA-256 校验，不暴露静态文件路径。

## 6. 兼容性

- 旧草稿没有 `receiptNo` 字段：恢复时补空串，查重快照被丢弃。
- 历史收据号存在空格/中文（导入遗留），本规则仅约束**新制单**；财务核对环节仍允许按原口径补录。
- 旧价格状态字段 `priceLocked` 已随文字链 UI 一并删除，改由卡片本地 `editingPrice` + 数值比较驱动。
