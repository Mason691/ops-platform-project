# 业务订单「退回草稿 / 作废退款」— 规格说明

> 状态：✅ 已开发并部署生产（2026-11-18）；生产 E2E 已通过（见第十一节）；仅微信真机点击待人工确认（平台消息发送日志已 SUCCESS）
> 范围：ops 员工 H5 订单详情/草稿编辑 + ops 后端退款与工作流 + 平台工作流定义/字典 + 统计口径

## 一、功能概述

员工工作台「业务数据订单」详情在业务状态未到「3 派工出库」前提供：

- **退回草稿**：终止当前审批实例 → `biz_status=0`、`draft_flag=1`；订单详情出现「编辑订单」，
  复用现有 5 步制单向导修改全部可编辑字段；提交后沿用原订单编号/业务组号重新进入审批。
- **发起退款申请**：填写退款原因/金额/备注/补充附件 → 终止正常审批 → 启动「业务订单作废工作流」
  （部长审核 → 财务审核 → 总经办审核）→ 全部通过后订单 `biz_status=-1` 锁定。
- **重新提交审批**：作废退款被驳回/终止后，订单恢复原业务状态，可一键重新发起正常审批（草稿可编辑后提交）。
- 平台数据字典新增 `business_order_status = -1 / 作废退款`；平台列表/详情/筛选读取字典并以红色标签展示。

## 二、关键决策（需求要求明确）

1. **操作人**：任一经办人可发起（默认，不要求全部经办人同意）；服务端按订单 `agent_phones`/创建人校验。
2. **退回草稿的流程处理**：**终止**当前流程实例（不是回退到发起节点），平台把待办置为 SKIPPED 并发送终止消息；
   重新提交时创建新实例，旧待办/旧消息不再指向。
3. **重新提交**：沿用原 `order_no` / `business_group_no`，不重新生成订单编号；重新进入部长审核。
4. **退款驳回规则**：部长/财务驳回 → 退回经办人（实例 REJECTED）；总经办驳回 → 退回上一节点（财务，实例继续）。
5. **退款期间正常流程**：发起退款时终止正常流程，避免审批期间推进到派工出库；退款驳回后不恢复已终止实例，
   由「重新提交审批」从部长节点重新开始（平台不支持恢复已终止实例的中间节点）。
6. **已出库/已上报集团/已生成以旧换新采购单**：两项操作均拦截；SCM 不可达 fail-closed（不允许在无法校验时继续）。
7. **作废后处理**：订单 `biz_status=-1`、`draft_flag=0`、订单/明细 `calc_status=已作废`、明细提成置 0；
   订单锁定，不可编辑/派工/再退款；统计排除。
8. **退款金额**：默认订单应付合计，可下调但不得超过；退款原因必填（≤500 字）；
   金额低于应付合计时备注必填（≤500 字，用于说明调整理由）。
9. **退款补充附件**：复用业务附件上传（`fileType=REFUND`），JPG/PNG/PDF，最多 5 个，单个 ≤10MB，图片压缩。
10. **审批中限制**：不可重复发起退款、不可退回草稿、不可编辑；退款驳回后可重新发起或（草稿态）编辑。
11. **工作日志**：平台 `wf_log` 记录流程发起/审批/驳回/终止；H5 工作日志新增「业务订单作废」筛选项。
12. **统计口径**：作废订单保留在列表供审计，但不计入员工销售/提成合计、员工月度/品类统计、管理端汇总、
    品类提成汇总与作战地图；作战地图原 `calc_status IN (已计算/经办人已核对/已上报集团)` 天然排除「已作废」。

## 三、工作流配置（平台库 `ai_platform`）

定义：`biz_order_void_flow` / `business_type=OPS_BUSINESS_ORDER_VOID` / `PUBLISHED`，
回调 `http://localhost:8082/api/internal/workflow/business-order/event`。

| 序号 | 节点 | 类型 | 模式 | bizStatus | 驳回 | 动作 | 审批人 |
|---|---|---|---|---|---|---|---|
| 1 | 作废申请 | START | ANY | NULL | INITIATOR | — | — |
| 2 | 部长审核 | APPROVAL | ANY | NULL | INITIATOR | `OPS_VOID_MINISTER` | 部长 @ INITIATOR_CORP |
| 3 | 财务审核 | APPROVAL | ANY | NULL | INITIATOR | `OPS_VOID_FINANCE` | 财务 @ INITIATOR_CORP |
| 4 | 总经办审核 | APPROVAL | ANY | NULL | PREVIOUS | `OPS_VOID_COMPLETE`（末节点） | 总经办 @ OPERATOR_TREE |

- `biz_status=NULL`：作废流程不覆盖订单原业务状态（0/1/2），仅终审动作置 -1。
- 消息模板复用现有 `TASK_CREATED/APPROVED/REJECTED/TERMINATED`；跳转 URL 必须同时含 `{taskId}`/`{instanceId}`。
- 平台新增内部终止接口 `POST /api/internal/wf/instance/{id}/terminate`（`X-Internal-Token`），供退回草稿/发起退款使用。

## 四、数据模型（ops 库 `mall_db`）

- `ops_business_order.draft_flag TINYINT NOT NULL DEFAULT 0`（1=退回草稿待编辑重提）。
- 新表 `ops_business_refund`：
  `corp_id/order_id/refund_no/reason/amount/attachment_urls/attachment_ids/status/
   original_biz_status/wf_instance_id/wf_node_order/wf_node_name/applicant_*/reject_reason/approved_time`
  + BaseEntity 审计字段；`status=PENDING/APPROVED/REJECTED/TERMINATED`。
- `ops_business_attachment` 新增 `REFUND` 类型（无需改表结构）。
- 平台字典 `business_order_status` 新增 `-1 / 作废退款`。

## 五、API（员工 JWT，拒绝 sso 会员令牌）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ops/employee/business-data/orders/{orderId}/return-draft` | 退回草稿 |
| POST | `/api/ops/employee/business-data/orders/{orderId}/refund` | 发起退款 `{reason, amount, remark, attachmentIds}` |
| GET | `/api/ops/employee/business-data/orders/{orderId}/refund` | 最近退款 + 流程进度 |
| POST | `/api/ops/employee/business-data/orders/{orderId}/restart-flow` | 驳回后重新提交审批 |
| GET | `/api/ops/employee/business-data/orders/{orderId}/edit` | 草稿编辑回显（订单头+商品/旧品/凭证） |
| PUT | `/api/ops/employee/business-data/orders/{orderId}/draft` | 草稿编辑提交（沿用原订单编号） |

订单详情响应新增：`draftFlag`、`refund`、`canReturnDraft`、`canApplyRefund`、`canEdit`、`canRestartFlow`；
列表响应新增 `draftFlag`、`refundStatus/refundStatusName`（作废审批中）。

## 六、安全与一致性

- 仅员工 JWT；经办人校验（`agent_phones` 或创建人）；`corp_id` 只从 JWT。
- 退回/退款/重新提交在事务内 `SELECT ... FOR UPDATE` 锁订单行，避免并发产生重复退款/重复流程。
- 状态守卫：仅 0/1/2；已出库（SCM 查询，fail-closed）、已上报集团、已生成以旧换新采购单、已有 PENDING 退款拦截。
- 附件复用订单级归属校验；草稿编辑允许复用已绑定到本订单的附件（支持其他经办人上传）。
- 作废流程回调按 `taskId + actionType` 幂等；终审动作在 `markApproved` 独立事务内完成，留痕失败由平台重试并按幂等返回。
- 作废流程每个节点重新校验订单仍可作废（状态/出库/上报/采购），fail-closed。

## 七、前端交互

- 订单详情：草稿/作废标签；操作卡片（编辑/退回草稿/发起退款/重新提交）；退款进度卡片（金额、原因、驳回原因、当前节点/处理人、附件）。
- 退款表单：金额（默认应付合计、≤上限）、原因（必填）、备注、补充附件；提交后刷新。
- 编辑：复用 `business-data-new.vue`（`?orderId=`），回显全部字段，提交成功页显示「重新提交成功」。
- 列表：草稿、作废审批中、作废退款标签；作废订单保留展示，合计不含作废。
- 待办处理页：作废节点展示退款申请信息，复用通用同意/驳回。
- 工作日志：新增 `OPS_BUSINESS_ORDER_VOID` 筛选项。

## 八、验收标准

1. 状态 0/1/2 时经办人可见两按钮；状态 ≥3 不可见且接口拦截。
2. 退回草稿后状态 0、草稿标记、编辑入口；修改提交后订单编号不变、旧待办失效、新待办/消息生成。
3. 退款后部长/财务/总经办依次收到待办与公众号消息，消息可跳转待办页。
4. 三级通过后状态 -1、订单锁定；任一驳回按规则退回，订单不进入 -1。
5. 退款金额 ≤ 应付合计、原因必填校验生效。
6. 字典 -1 存在，列表/详情/筛选可用，红色标签。
7. 作废订单不参与提成/有效业绩统计；工作日志完整。
8. 非经办人、已出库、已上报集团订单接口拒绝。

## 十、已知限制

- 退款驳回后从部长节点重新开始（平台不支持恢复已终止实例的中间节点）。
- 作废流程节点 `biz_status=NULL`，审批期间订单列表仍显示原业务状态，另以 `refundStatus` 标记「作废审批中」。
- 历史已压缩/已绑定附件不做迁移；草稿编辑替换凭证时旧附件解绑，由附件清理任务删除。
- 平台主站仅新增 -1 红色标签与字典筛选项；更细的作废统计看板未新增。
- 微信真机点击待人工确认：平台 `wf_message_send_log` 已记录 TASK_CREATED/APPROVED/REJECTED `send_status=SUCCESS`，未绑定公众号的员工为 `SKIPPED`（预期）；跳转 URL 已含 `taskId` 与 `instanceId`。
- 退款金额下调时备注必填（前后端双重校验），防止无依据少退。
